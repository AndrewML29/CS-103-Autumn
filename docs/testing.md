# Проверки вариантов

В каждом варианте есть `tests.json`: входные данные, ожидаемые результаты,
договорённости о формате и границы проверки. Решения в репозиторий не добавлены.
**Пустые заготовки должны проваливать содержательные тесты.**

## Что проверяется

- `io`: выполнение `Task()`, код завершения и результат в stdout.
- `function`: значения `Func(x)` для Тейлора, включая границы отрезка.
- `model`: входные и итоговые слова/ленты алгоритмических моделей.
- `shell`: stdout и изменения файлов после отдельного bash-задания.
- `manual`: проверочный список для LaTeX, без автоматической отметки «сдано».
- `blocked`: исходное условие неполно или противоречиво. Проверка завершается
  ошибкой с причиной, а не успешным пропуском.

Полное покрытие и список препятствий: [tests/README.md](../tests/README.md).

Новые соглашения в `contract` нужны потому, что оригинальные условия не задавали
машиночитаемые форматы. Это уточнения тестового интерфейса, а не готовые решения.
Для неоднозначных содержательных требований (например, неизвестной геометрической
области) ожидаемые ответы не выдумываются.

## C/C++

Из корня репозитория:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target integers1 --parallel 2
ctest --test-dir build -R '^integers1$' --output-on-failure
```

Вместо `integers1` укажите раздел и номер варианта, например `matrix20`.
Можно запустить `./build/integers1` напрямую. Имена тестов и фактический/ожидаемый
вывод видны в диагностике Catch.

Один сценарий выполняется в отдельном процессе и временном каталоге. Его вход
доступен через stdin и файл `input.txt`; FSM и матрицы по условию читают файл.
Вывод пишется в stdout. `Task()` возвращает 0 при успешном выполнении. Лимит одного
сценария — 3 секунды; состояние файлов и EOF не переносится между сценариями.

Обычно сравниваются токены: количество пробелов и переводов строк несущественно.
Лишние подписи/приглашения запрещены. Исключения и числовая точность указаны в
`tests.json`. NaN и бесконечность не считаются допустимыми числовыми ответами.

Для Тейлора проверяется существующий интерфейс `long double Func(long double x)`.
Эти тесты **не проверяют** таблицу из `Task()`, использование ряда и число итераций.
Для линеризации проверяются N=1 и N=4 по опубликованному рисунку; обобщение на другие
размеры требует отдельной проверки. Для численных методов проверяются корни, а не
выбор метода и доказательство сходимости. Ожидаемые значения рассчитаны по формулам
на рисунках; округлённый столбец ответов на рисунках не является точным эталоном.

Санитайзеры включены по умолчанию. Для диагностики проблем среды в **новом** каталоге
сборки можно передать `-DENABLE_SANITIZERS=OFF`. Проверка вывода сама по себе не
доказывает отсутствие всех ошибок памяти; дочерний процесс завершается через
`_exit`, поэтому финальная проверка утечек дочернего процесса не гарантируется.

## Linux

```sh
python3 tools/check_task.py tasks/linux/tasks/1
```

Каждый из десяти скриптов выполняется через bash в отдельном временном каталоге.
`setup` задаёт файлы, каталоги, содержимое, размер и права; `checks` задаёт ожидаемое
состояние. Для `ifconfig` используется локальный тестовый вывод, а не сеть машины.
Поиск проверяется только по созданным входным файлам. Скрипты не копируются внутрь
каталога поиска. Это изоляция тестовых данных, а не защитная песочница ОС.

В варианте 2, скрипте 3 не определён формат архива; в варианте 5, скрипте 5 — путь
назначения копирования. Эти сценарии возвращают ошибку до уточнения условий.
Остальные сценарии запускаются, даже если один из них не прошёл.

## Нормальные алгоритмы Маркова

```sh
python3 tools/check_task.py tasks/nam/tasks/1
```

Встроенный интерпретатор читает `solution.nam`. Правила имеют вид `src->dst`,
терминальные — `src->.dst`; `src->.` удаляет подстроку и завершает выполнение.
Выбирается первое применимое правило и самое левое вхождение, затем поиск правил
начинается сверху. Пустая левая часть допустима. Строки, начинающиеся с `#` или `//`,
считаются комментариями. Для буквального пробела в правиле используйте `\s`.
Лимиты: 100000 подстановок, 100000 символов слова и 5 секунд на сценарий.
Это дополнительные пределы тестового запуска, не требование к сложности алгоритма.

## Машины и диаграммы Тьюринга

`tests.json` содержит исходную и полную итоговую ленту, включая сохранённый ввод.
Их можно проверять вручную в эмуляторе или подключить исполняемый адаптер:

```sh
python3 tools/check_task.py tasks/turing_machine/tasks/1 \
  --command /absolute/path/to/emulator-adapter /absolute/path/to/solution.tu
```

Адаптер получает начальную ленту через stdin и пишет итоговую ленту в stdout.
Он должен загрузить **студенческую машину**, исполнить её и вернуть ненулевой код
при ошибке. Используйте абсолютные пути: рабочая папка каждого запуска временная.
Репозиторий не содержит универсального адаптера к внешним GUI-эмуляторам и не
объявляет такие работы автоматически проверенными без адаптера.

Тот же протокол `--command` можно использовать для отдельной консольной программы
или другого интерпретатора Маркова. Для численных задач он получает epsilon,
для функций Тейлора — x. Диаграммы, ограничения алфавита и асимптотика проверяются
на защите: несколько входов не доказывают требуемую сложность.

## Для преподавателя: сопровождение

```sh
# Структура тестов во всех вариантах; это не проверка решений:
python3 tools/check_task.py --audit
# Строгий отчёт о всех ещё не автоматизированных/неопределённых заданиях:
python3 tools/check_task.py --audit --require-complete
# После правок tests.json обновить Catch-тесты:
python3 tools/render_tests.py
# Убедиться, что test.cpp соответствуют tests.json:
python3 tools/render_tests.py --check
# Проверить сам механизм тестирования:
python3 -m unittest discover -s tools/tests -v
cmake --build build --target test_task_check
ctest --test-dir build -R '^infrastructure_' --output-on-failure
```

Генератор курса сохраняет `test.cpp` вариантов, у которых есть `tests.json`.
Остальные режимы генератора по-прежнему могут перезаписывать заготовки решений и
условия: не запускайте `--files`/`--description` над выполненными работами без копии.

CI отдельно проверяет инфраструктуру и соответствие сгенерированных тестов.
В PR проверки решений и линтеры запускаются для изменённых файлов решений;
нерешённые соседние варианты не мешают сдаче. Изменение только условий/тестов
не запускает нерешённые заготовки как готовые работы. Содержательную корректность
новых ожидаемых ответов преподаватель проверяет на ревью.

Успешный структурный аудит не означает, что задачи решены, и не скрывает
`blocked`/`manual`: строгий аудит возвращает ненулевой код, пока они существуют.
